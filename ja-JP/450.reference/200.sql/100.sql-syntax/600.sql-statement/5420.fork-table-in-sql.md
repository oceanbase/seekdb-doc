# FORK TABLE

## 説明

`FORK TABLE` 文は、指定された一貫性スナップショット時点で、ソーステーブルの論理的に等価なターゲットテーブルのコピーを作成します。ターゲットテーブルは独立したテーブルオブジェクトとして後続の読み書き操作に使用でき、ターゲットテーブルとソーステーブルは相互に分離されているため、いずれか一方のテーブルへの書き込みはもう一方に影響しません。

従来の「データの完全コピー」方式と比較して、Fork Tableはスナップショットの一貫性セマンティクスを保証する前提で、既存のデータ構造とストレージ構造を可能な限り再利用することで、大規模テーブルのコピーにかかる時間とリソースコストを削減します。

:::tip
seekdb V1.1.0では、Fork Tableは実験的機能です。本番環境での使用は慎重に行ってください。
:::

## 権限要件

`FORK TABLE` を実行するには、通常、以下の権限要件を満たす必要があります：

* ソーステーブルへのアクセス権限（例：`SELECT`）。
* ターゲットテーブルが存在するデータベースでテーブルを作成する権限（例：`CREATE`）。

その後、ターゲットテーブルで読み書きまたはDDL操作を実行する場合は、対応するテーブル/データベース権限が必要です。

## 構文

```sql
FORK TABLE source_table TO destination_table;
```

## パラメータの説明

| **パラメータ** | **説明** |
|---|---|
| source_table | ソーステーブル名。`db.table` または `table` を指定できます（現在のデータベースを使用する場合）。 |
| destination_table | デスティネーションテーブル名。`db.table` または `table` を指定できます（現在のデータベースを使用する場合）。 |

## 行動の説明

* **スナップショットの一貫性**：ターゲットテーブルのデータビューは、Fork時点でのソーステーブルの一貫性スナップショットと一致します。Fork後にソーステーブルで発生した追加/変更/削除はターゲットテーブルに影響しません。

* **読み書きの分離**：ターゲットテーブルとソーステーブルは相互に独立しています。ターゲットテーブルへの書き込みはソーステーブルに影響せず、ソーステーブルへの書き込みもターゲットテーブルに影響しません。

* **段階的な可用性**：システムはターゲットテーブルオブジェクトの作成を優先し、迅速にアクセス可能にします。バックグラウンドでは必要なデータ構築作業が継続される可能性がありますが、外部に対しては常に一貫したスナップショットセマンティクスと可用性を提供します。

* **パフォーマンス特性**：典型的な小規模シナリオでは、`FORK TABLE` は数百ミリ秒でターゲットテーブルの作成を完了し、即座に利用可能になります。大規模テーブル/複雑な負荷シナリオでは、バックグラウンド処理により時間がかかる場合があります。

## 使用制限と注意事項

seekdb V1.1.0におけるFork Tableの使用制限と注意事項は以下の通りです：

* **DDLとの排他性**：Forkプロセスは通常、ソーステーブルの日常的な読み書きに影響しませんが、このプロセス中はソーステーブルとターゲットテーブルがDDL操作と排他的になるため、Fork操作が終了するまで注意が必要です。関連するテーブルに対して `CREATE/ALTER/DROP/RENAME` などのDDLを同時に実行することは避けることを推奨します。

* **ターゲットテーブルは存在してはならない**：ターゲットテーブルが既に存在する場合、システムはエラーを返します。既存のターゲットテーブルを削除してから再度試してください。

* **オブジェクトタイプの制限**：一部のオブジェクトに対するForkはサポートされていません。これには、内部テーブル、一時テーブル、マテリアライズドビュー、トリガー、外部キー、およびゴミ箱内のテーブルが含まれます。

* **インデックス関連の制限**：
  * セマンティックインデックス、IVFインデックス、空間インデックスはサポートされていません。
  * グローバルインデックスを含むパーティションテーブルに対するForkはサポートされていません。
  * Fork構築プロセス中のインデックス構築はサポートされていません。インデックス戦略の調整が必要な場合は、Fork完了後にターゲットテーブルで `CREATE INDEX`/`ALTER TABLE` などの操作を実行してください。
  * ソーステーブルにHNSWベクトルインデックスが含まれる場合、Fork操作は追加のメモリ負荷を引き起こす可能性があります。リソースが限られている環境では、まず小規模で検証し、モニタリングと容量計画を適切に行うことを推奨します。
* **ストレージ形態の制限**：Forkカラムストアテーブルはサポートされていません。

## 例

### 例1：レプリカテーブルを作成し、読み書きを実行する

```sql
-- テーブルのレプリカを作成
FORK TABLE t1 TO t1_fork;

-- レプリカテーブルはクエリ可能
SELECT count(*) FROM t1_fork;

-- レプリカテーブルに書き込み可能（書き込みはソーステーブルt1に影響しない）
INSERT INTO t1_fork VALUES (...);
```

### 例2：データバージョンとブランチの管理（ブランチのロールバック/プッシュ）

```sql
-- 1) プライマリバージョンに基づいてブランチバージョンを作成（データベースラインはFork時点のスナップショット）
FORK TABLE t1 TO t1_branch_v2;

-- 2) ブランチ上で実験的な変更を行う（例：データの修正/機能の更新/インデックスとメタデータ戦略の調整など）
-- ... t1_branch_v2に対してDML/業務プロセスを実行 ...

-- 3a) ロールバック：ブランチバージョンの使用を停止する（例：ブランチテーブルを削除）
DROP TABLE t1_branch_v2;

-- 3b) プッシュ：ブランチバージョンを新しいデフォルトバージョンとして適用する（例：原子的RENAMEによる切り替え）
-- RENAME TABLE t1 TO t1_branch_backup, t1_branch_v2 TO t1;
-- DROP TABLE t1_branch_backup;
```

### 例3：A/Bテストとサンドボックス検証

```sql
-- オンラインテーブルをベースラインとして実験テーブルを作成
FORK TABLE t_search_prod TO t_search_exp;

-- 実験テーブル上で変更と評価を行う（インデックス/メタデータ/アルゴリズム関連パラメータなど）
-- ... t_search_expに対して実験的な書き込みとクエリ評価を実行 ...

-- 実験が失敗した場合：実験テーブルの使用を停止し、オンラインテーブルに戻る
DROP TABLE t_search_exp;
```

## よくある質問

### Q1：Fork完了後、ソーステーブルの後続変更はターゲットテーブルに影響しますか？

影響しません。ターゲットテーブルはFork時点の一貫性スナップショットに基づいて作成されるため、ソーステーブルで後から発生した変更はターゲットテーブルに反映されません。

### Q2：ターゲットテーブルを変更するとソーステーブルに影響しますか？

影響しません。ターゲットテーブルとソーステーブルは相互に隔離されており、いずれか一方のテーブルへの書き込みはもう一方に影響しません。

### Q3：なぜForkが完全に終了する前にターゲットテーブルを使用できるのですか？

システムはターゲットテーブルオブジェクトの作成を優先的に完了し、アクセス機能を提供します。バックグラウンドでのデータ整理プロセス中でも、システムは外部に一貫したスナップショットの意味合いと可用性を保証します。同時に、`FORK TABLE` は作成段階で既存のデータ整理およびストレージ構造を可能な限り再利用するため、大規模テーブルの場合でも通常は比較的高速な作成速度を維持できます。

### Q4：FORK TABLEと従来のテーブルコピーアクティビティは何が違いますか？

`FORK TABLE` は一貫性の意味合いを満たす前提で既存のデータ整理およびストレージ構造を可能な限り再利用し、全量データコピーに伴う時間とリソースのコストを削減します。
