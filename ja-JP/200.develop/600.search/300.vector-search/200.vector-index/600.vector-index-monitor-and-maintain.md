# インデックスの監視とメンテナンス

このドキュメントでは、seekdbベクトルインデックスの監視とメンテナンス方法について説明します。

## モニタリング

システムビューを使用すると、ベクトルインデックスの基本情報とリアルタイム状態を確認できます。

* [[G]V$OB_HNSW_INDEX_INFO](https://www.oceanbase.com/docs/common-oceanbase-database-cn-1000000004477829) ビューを使用して、HNSWシリーズインデックスの基本情報とリアルタイム状態を確認できます。
* [[G]V$OB_IVF_INDEX_INFO](https://www.oceanbase.com/docs/common-oceanbase-database-cn-1000000004477818) ビューを使用して、IVFシリーズインデックスの基本情報とリアルタイム状態を確認できます。

## メンテナンス

増分データが過剰な場合、検索性能が低下します。増分データテーブルのデータ量を削減するため、SEEKDBデータベースはベクトルインデックスのメンテナンスに `DBMS_VECTOR` を導入しています。

### 増分リフレッシュ

:::tip
この機能はHNSWシリーズインデックス、セマンティックインデックス、メモリ疎インデックスをサポートしていますが、IVFシリーズインデックスはサポートしていません。
:::

:::tip
セマンティックインデックスで非同期埋め込みモードを使用している場合、増分リフレッシュ時にデータの埋め込みが追加でトリガーされ、増分データが正しくベクトルに変換されてインデックスに追加されることを保証します。
:::

インデックス作成後にデータの書き込みが多い場合は、`REFRESH_INDEX` プロシージャを使用した増分リフレッシュを実行することを推奨します。説明と例については、[REFRESH_INDEX](../../../../450.reference/300.pl/1000.pl-system-package/17850.dbms-vector/200.refresh-index.md)を参照してください。

増分リフレッシュは15分ごとにチェックされ、増分データが1万件を超えた場合に自動的に実行されます。

### フル更新（再構築）

#### 手動によるテーブル全体の再構築

インデックス作成後にデータの更新や削除が多い場合は、`REBUILD_INDEX` プロシージャを使用してフルリフレッシュすることを推奨します。説明と例については、[REBUILD_INDEX](../../../../450.reference/300.pl/1000.pl-system-package/17850.dbms-vector/300.rebuild-index.md) を参照してください。

フルリフレッシュは24時間ごとにチェックされ、新規データが既存データの20%を超えた場合に自動的に実行されます。フルリフレッシュはバックグラウンドで非同期に実行され、まず新しいインデックスを作成し、その後古いインデックスを置き換えます。再構築中は古いインデックスも利用可能な状態が保たれますが、全体的にプロセスは比較的遅くなります。

また、`vector_index_memory_saving_mode` 構成パラメータを提供しており、インデックス再構築時のメモリ使用量を制御できます。このモードを有効にすると、パーティションテーブルのベクトルインデックス再構築（rebuild）プロセス中のメモリ消費を削減できます。通常、ベクトルインデックスの再構築にはインデックスサイズの2倍のメモリが必要です。メモリ節約モードを有効にすると、システムはパーティションテーブルの各パーティションの構築が完了した後、そのパーティションのメモリインデックスを一時的に削除することでメモリを解放し、再構築操作に必要な総メモリを効果的に削減します。構文と例については、[vector_index_memory_saving_mode](https://www.oceanbase.com/docs/common-oceanbase-database-cn-1000000004478889) を参照してください。

注意事項は以下の通りです：

* [オフラインDDL](../../../../450.reference/200.sql/100.sql-syntax/700.ddl-function/150.online-and-offline-ddl-list.md) 操作（例：`ALTER TABLE` によるテーブル構造や主キーの変更）を実行すると、インデックステーブルの再構築が発生します。インデックスの再構築では並列度を指定できないため、システムはデフォルトで単一スレッドを使用します。そのため、データ量が多い場合、再構築プロセスが遅くなり、結果としてオフラインDDL全体の実行効率に影響します。
* インデックスの再構築時にパラメータを変更する必要がある場合は、`type` と `distance` をパラメータリストに同時に指定する必要があり、かつ `type` と `distance` は元のインデックスタイプと一致している必要があります。例えば、元のインデックスタイプが `hnsw`、距離アルゴリズムが `l2` の場合、再構築時には `type=hnsw` と `distance=l2` を同時に指定する必要があります。
* インデックスの再構築時には以下がサポートされます：
    * `m`、`ef_search`、`ef_construction` の値を変更すること。
    * `ef_search` パラメータのオンライン再構築。
    * `hnsw` と `hnsw_sq` インデックスタイプ間の相互変換による再構築。
    * `ivf_flat` と `ivf_flat`、`ivf_pq` と `ivf_pq` インデックスタイプ間の相互変換による再構築。
    * 再構築時の並列度設定をサポートします。例については [REBUILD_INDEX](../../../../450.reference/300.pl/1000.pl-system-package/17850.dbms-vector/300.rebuild-index.md) を参照してください。

* インデックスの再構築時には以下はサポートされません：
    * `type` と `distance` タイプの変更。
    * `hnsw` と `ivf` インデックスタイプ間の相互変換による再構築。
    * `hnsw` と `hnsw_bq` インデックスタイプ間の相互変換による再構築。
    * `ivf_flat`、`ivf_pq` 間の交差再構築。

#### 自動パーティション再構築（推奨）

:::tip
この機能はHNSWシリーズインデックス、セマンティックインデックス、メモリ疎インデックスをサポートしていますが、IVFシリーズインデックスはサポートしていません。
:::

:::tip
セマンティックインデックスは自動パーティション再構築時に増分データとスナップショットタスクを同時に処理し、インデックスデータの一貫性と完全性を確保します。
:::

現在のバージョンでは、自動パーティション再構築タスクがトリガーされるシナリオは2つあります：

* ベクトルインデックス検索ステートメントを実行する場合。
* 定期的なチェックで、実行間隔は手動で設定できます。

1. 実行間隔の設定

    `oceanbase` データベースで、パラメータ [vector_index_optimize_duty_time](https://www.oceanbase.com/docs/common-oceanbase-database-cn-1000000004478820) を使用して実行間隔を設定します。例：

    ```sql
    ALTER SYSTEM SET vector_index_optimize_duty_time='[23:00:00, 24:00:00]';
    ```
    上記の設定が完了すると、パーティション再構築タスクは23:00:00～24:00:00の時間帯にのみ実行され、他の時間帯では開始されません。詳細なパラメータ説明については、該当するパラメータドキュメントを参照してください。

2. タスクの進捗状況/履歴タスクの確認

    [CDB/DBA_OB_VECTOR_INDEX_TASKS](https://www.oceanbase.com/docs/common-oceanbase-database-cn-1000000004478170) または [CDB/DBA_OB_VECTOR_INDEX_TASK_HISTORY](https://www.oceanbase.com/docs/common-oceanbase-database-cn-1000000004477461) ビューを使用して、タスクの進捗状況や履歴タスクを確認できます。

    `status` フィールドでタスクの現在の状態を判断します：

    * 0 (PREPARE)：タスクが実行待ちです。
    * 1 (RUNNING)：タスクが実行中です。
    * 2 (PENDING)：タスクの実行が一時停止されています。
    * 3 (FINISHED)：タスクが完了しました。

    実行終了したタスク、つまり `status=FINISHED` のタスクは、実行成功の有無にかかわらず履歴テーブルに転送されます。詳細な使用例については、該当するビュードキュメントを参照してください。

3. タスクのキャンセル

    タスクをキャンセルする場合は、`DBA_OB_VECTOR_INDEX_TASKS` または `CDB_OB_VECTOR_INDEX_TASKS` ビューで trace_id を取得し、以下のコマンドを実行します：

    ```sql
    ALTER SYSTEM CANCEL TASK <trace_id>;
    ```
    例：
    ```sql
    ALTER SYSTEM CANCEL TASK "Y61480BA2D976-00063084E80435E2-0-1";
    ```
