# Forkテーブル

Forkテーブルは、seekdbが提供するテーブルレベルの機能であり、システムが自動的に選択したスナップショット時点に基づいて、ソーステーブルからターゲットテーブルのコピーを作成できます。ターゲットテーブルはソーステーブルと相互に隔離され、独立したテーブルオブジェクトとして後続の読み書き操作に使用できます。本記事では、Forkテーブルの機能と典型的な使用方法について説明します。ステートメント構文、パラメータ、および完全な制限事項については、記事末尾の関連ドキュメントを参照してください。

:::tip
seekdb V1.1.0バージョンでは、Forkテーブルは実験的な機能です。本番環境での使用は慎重に行ってください。
:::

## 機能の概要

開発やイテレーションの過程で、データの修正、特徴量エンジニアリング、インデックスやメタデータ戦略の調整など、異なるシナリオを同一のデータベースラインから並行して検証する必要が生じることがあります。従来の方法でテーブルデータを全量コピーする場合（例：`CREATE TABLE ... AS SELECT ...` またはエクスポート・インポート）、大規模なテーブルでは時間とリソースのコストが高くなる可能性があります。

Fork Tableは、システムが自動的に選択した整合性スナップショット時点で、ソーステーブルからターゲットテーブルのコピーを作成します。ターゲットテーブルは論理的にそのスナップショット時点のソーステーブルのデータビューと等価であり、独立したテーブルオブジェクトとして後続の読み書き操作に使用できます。Fork Tableの設計目標は、整合性セマンティクスを保証する前提で、既存のデータ組織とストレージ構造を可能な限り再利用し、レプリケーションのオーバーヘッドを低減し、データブランチの作成をより軽量かつ使いやすくすることです。

## 適用シナリオ

* **データバージョンとブランチ管理**：同一のベースラインデータから複数のブランチバージョンを派生させ、それぞれでデータの修正、特徴量の更新、インデックス/メタデータ戦略の調整を行い、追跡可能なバージョン関係を保持します。同時に、Fork Tableは迅速なロールバックをサポートしており、ブランチの検証結果が期待に達しない場合は、そのブランチの使用を直ちに中止して元のバージョンに戻ることができます。ブランチの検証結果が期待に達した場合は、そのブランチの結果を新しいデフォルトバージョンとして適用することができます（具体的な切り替え方法は業務および運用プロセスに準じます）。
* **A/B実験とサンドボックス検証**：本番データのスナップショットから隔離されたコピーを作成し、そのコピー上で異なるPrompt戦略、AI Coding生成ロジック、または大規模モデルの推論動作を安全に検証します。複数のシナリオを比較でき、オンラインテーブルに影響を与えません。
* **Vibe Codingと合成データによるイテレーション**：Forkによって作成されたコピー内でデータ構造や内容を生成または変更し、合成データセットを迅速に構築してその妥当性を検証します。

## 動作メカニズム

Fork Tableの主要なセマンティクスは以下の通りです：

* **スナップショットの整合性**：ターゲットテーブルは、Fork時点でのソーステーブルの整合性スナップショットを反映しており、その後のソーステーブルの変更はターゲットテーブルに影響しません。
* **読み書きの分離**：ターゲットテーブルとソーステーブルは相互に独立しており、いずれか一方のテーブルへの書き込みはもう一方に影響しません。
* **段階的な可用性**：ターゲットテーブルは、Forkが完全に終了する前にアクセス可能になります。バックグラウンドプロセスは外部への整合性セマンティクスや可用性を変更しません。

## 使用制限と注意事項

seekdb V1.1.0におけるFork Tableの使用制限と注意事項は以下の通りです：

* **DDLとの排他性**：Fork処理中は通常、ソーステーブルの日常的な読み書きには影響しませんが、この処理中はソーステーブルとターゲットテーブルがDDL操作と排他的になり、Fork操作が終了するまで継続します。関連するテーブルに対して `CREATE/ALTER/DROP/RENAME` などのDDLを同時に実行することは避けることを推奨します。
* **ターゲットテーブルは存在してはならない**：ターゲットテーブルが既に存在する場合、システムはエラーを返します。既存のターゲットテーブルを削除してください。
* **オブジェクトタイプの制限**：一部のオブジェクトに対してはForkをサポートしていません。これには、内部テーブル、一時テーブル、マテリアライズドビュー、トリガー、外部キー、およびゴミ箱にあるテーブルが含まれます。
* **インデックスに関する制限**：
  * セマンティックインデックス、IVFインデックス、空間インデックスはサポートされていません。
  * グローバルインデックスを含むパーティションテーブルに対してForkを実行することはサポートされていません。
  * Forkの構築過程でインデックスを作成することはサポートされていません。インデックス戦略の調整が必要な場合は、Fork完了後にターゲットテーブルで `CREATE INDEX`/`ALTER TABLE` などの操作を実行してください。
  * ソーステーブルにHNSWベクトルインデックスが含まれる場合、Fork操作は追加のメモリ負荷を引き起こす可能性があります。リソースが限られている環境では、まず小規模な検証を行い、モニタリングと容量計画を適切に行うことを推奨します。
* **ストレージ形態の制限**：Forkカラムストアテーブルはサポートされていません。

## 例：テーブルレプリカを作成し、分離レベルを検証する

以下の例は、Fork Tableの基本的な使用手順を示しています：テーブルの作成 → Fork → テーブルオブジェクトとデータの整合性の検証 → 書き込み分離レベルの検証。

1. ソーステーブルを作成し、データを書き込みます。

    ```sql
    DROP TABLE IF EXISTS t1;
    DROP TABLE IF EXISTS t1_fork;

    CREATE TABLE t1 (
      c1 INT PRIMARY KEY,
      c2 INT
    );
    INSERT INTO t1 VALUES(1, 10);
    ```

2. ソーステーブルに基づいて、ターゲットテーブルのレプリカを作成します。

    ```sql
    FORK TABLE t1 TO t1_fork;
    ```

3. ターゲットテーブルのオブジェクトとデータの整合性を検証します。

    ```sql
    SHOW TABLES LIKE 't1%';
    SHOW CREATE TABLE t1_fork;

    SELECT COUNT(*) FROM t1;
    SELECT COUNT(*) FROM t1_fork;
    ```

4. 書き込み分離レベルを検証します：ターゲットテーブルへの書き込みはソーステーブルに影響しません。

    ```sql
    INSERT INTO t1_fork VALUES (2, 200);
    SELECT * FROM t1_fork;
    SELECT * FROM t1;  -- ソーステーブルには依然として (1, 10) のみが存在する
    ```

## よくある質問

### Q1：Fork完了後、ソーステーブルでの後続の変更はターゲットテーブルに影響しますか？

影響しません。ターゲットテーブルはFork時点の整合性スナップショットに基づいて作成されるため、その後ソーステーブルで発生した変更はターゲットテーブルに反映されません。

### Q2：ターゲットテーブルを変更すると、ソーステーブルに影響しますか？

影響しません。ターゲットテーブルとソーステーブルは相互に分離されており、いずれか一方のテーブルへの書き込みはもう一方に影響しません。

### Q3：なぜForkが完全に終了する前にターゲットテーブルを使用できるのですか？

システムは、ターゲットテーブルのオブジェクト作成を優先的に完了し、アクセス機能を提供します。バックグラウンドでのデータ整理プロセス中でも、システムは外部に対して一貫したスナップショットの意味合いと可用性を保証します。同時に、`FORK TABLE`は作成段階で既存のデータ整理およびストレージ構造の再利用を最大限図るため、大規模テーブルの場合でも通常は比較的高速な作成速度を維持できます。

### Q4：FORK TABLEと従来のテーブルコピーアクションとの違いは何ですか？

`FORK TABLE`は、整合性の意味合いを満たす前提で既存のデータ整理およびストレージ構造の再利用を最大限図ることで、全量データコピーに伴う時間とリソースのコストを削減します。
