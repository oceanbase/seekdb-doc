# フルテキストインデックスを体験する

## フルテキストインデックスの紹介

フルテキストインデックス（Full-Text Index）は、テキストデータの検索を高速化するためにデータベースで使用される特殊なインデックスタイプであり、特に記事の内容、コメント、ブログなど、多数のテキストフィールドを含むクエリニーズの処理に適しています。これは、キーワードによる高速なマッチングクエリをサポートし、テキスト内で1つまたは複数の単語を検索して関連する結果を返します。フルテキストインデックスは、検索エンジンやテキスト分析システムに広く用いられており、企業が重要な情報を迅速に特定し、検索効率を向上させるのに有効です。

企業の実際の運用において、フルテキストインデックス機能は、システムログ分析やユーザー分析など、多くのシナリオで活用できます。フルテキストインデックスは、データの高効率なフィルタリングや高品質な関連性評価を実現します。AI分野では、seekdbは疎密ベクトルとフルテキストインデックスを組み合わせたマルチリコールアーキテクチャに基づき、特定の知識領域を持つRAGシステムにおいて、より効率的で正確なリコール効果を実現します。

フルテキストインデックスの主な機能は以下の通りです：

* フルテキスト検索：フルテキストインデックスを構築することで、文書全体や長いテキスト内容を包括的にインデックス化し、より柔軟で効率的な検索を実現します。

* クイック検索：ユーザーは入力したキーワードに基づいてデータベース内で一致するテキストを迅速に検索でき、検索時間を大幅に短縮できます。

* 大量テキストの効率的処理：フルテキストインデックスは、記事、レポート、ウェブページ、電子メールなど、さまざまな種類のテキストデータを効果的に処理し、ユーザーに正確で迅速な検索体験を提供します。

* 複雑なクエリのサポート：基本的なキーワード検索に加え、フルテキストインデックスは近似検索や関連性ソートなどの複雑な検索ニーズもサポートし、データベースの検索機能を大幅に拡張します。

フルテキストインデックス機能を導入することで、seekdbは大規模なテキストデータと複雑な検索ニーズに直面した際に、クエリパフォーマンスを大幅に向上させ、ユーザーが必要な情報をより効率的に取得できるようにします。

## フルテキストインデックスを活用した大量ニュースデータの効率的な検索

以下の例では、ニュース情報業務シナリオを例に、フルテキストインデックス機能を利用して大量の情報からターゲットとなるニュースを迅速に検索する方法を示します。クエリ内のキーワードを通じて、seekdbフルテキストインデックスが機能、パフォーマンス、使いやすさの面でどのように向上しているかを紹介します。

### 前提条件

seekdbの全文インデックス機能を正常に操作および体験するには、以下の前提条件を満たしていることを確認してください：

1. **環境要件**：seekdbがデプロイ済みであること。

2. **データベースの作成**：データベースが作成されていることを確認してください。詳細な手順については、[データベースの作成](https://en.oceanbase.com/docs/common-oceanbase-database-10000000001971662)を参照してください。

### 手順

以下の手順に従って、seekdbの全文インデックスおよび一般的なビューとクエリのテクニックを体験してください。

#### ステップ１：データセットのインポート

seekdbには中国語をサポートするIK分かち書き器が組み込まれており、従来の自然言語処理よりも効率的なブールモードも備えています。[中国語サッカースポーツニュースデータセット](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/SeekDB/get-started/documents.csv)を使用してseekdbにデータをインポートし、`sport_data_whole`という名前の主キーのないパーティションテーブルを作成します。このテーブルには3つの可変長文字列列(`event`、`date`、`news`)が含まれます。また、IK中国語分かち書き器を使用して`news`フィールドに対して全文インデックスを作成し、`max_word`モードを指定します。

:::info
IK分かち書き器の<code>smart</code>モードと<code>max_word</code>モードの違いは、前者は最長の単語に一致した後、より短い単語へのマッチングを続けない点です。<br/>seekdbに組み込まれている他の分かち書き器には、英語に適したspaceやbeng、および文字長に基づいて分割するngramが含まれます。
:::

```sql
-- テーブルを作成し、IK分かち書き器を使用して全文インデックスを作成する
CREATE TABLE sport_data_whole (
    event VARCHAR(64),
    date VARCHAR(16),
    news VARCHAR(65535),
    FULLTEXT INDEX ft_idx1_news(news)
        WITH PARSER ik PARSER_PROPERTIES = (ik_mode = "max_word")
);
```

クライアントのローカルファイルを使用してニュースデータセットをテーブルにインポートすると、所要時間は約6.5秒です。

```sql
-- データをインポートする
LOAD DATA /*+ PARALLEL(8) */ LOCAL INFILE '/home/admin/sports_data_whole.csv' INTO TABLE sport_data_whole
FIELDS TERMINATED BY ',' LINES TERMINATED BY '\n';
```

データをインポートすると、テーブルには合計で100,000件のニュースがあり、平均ニュース長は約2,700字、元のデータサイズは約59MBです。効率的な圧縮後、実際のストレージ容量は30MBに満たず、その大部分は全文インデックス内の転置インデックスと正規インデックスの補助テーブルであり、多数の分かち書き記録が格納されています。

```sql

```

実行結果は次のとおりです：



#### ステップ2：全文インデックスを利用したクエリ

保存済みのニュースデータセットとインデックスを使用することで、複数の条件を組み合わせたり、高いフィルタリング精度で検索したりできます。例えば、サッカーファンが「バイエルン」と「オウンゴール」を含むニュースを検索したい場合、ブールモードを利用できます。

インデックスのない文字列 `LIKE` 比較に比べて、ブールモードは構文が簡潔で、クエリの実行速度も速くなります。

```sql
-- ブールモードを使用してクエリを実行し、「オウンゴール」と「バイエルン」の両方を含むニュースを検索します。
SELECT COUNT(*) FROM sport_data_whole
WHERE MATCH (news) AGAINST ('+オウンゴール +バイエルン' IN BOOLEAN MODE);
```

実行結果は次のとおりです：

```sql
+----------+
| COUNT(*) |
+----------+
|    14645 |
+----------+
1 row in set (0.03 sec)
```

対照的に、`LIKE` を使用したクエリの方法は次のとおりです：

```sql
-- LIKE 構文を使用してクエリを実行します。
SELECT COUNT(*) FROM sport_data_whole
WHERE news LIKE '%オウンゴール%' AND news LIKE '%バイエルン%';
```

実行結果も次のとおりです：

```sql
+----------+
| COUNT(*) |
+----------+
|    14645 |
+----------+
1 row in set (0.05 sec)
```

返された2つのニュースについて、ランキング（ranking）を行い、出力結果のスコアを比較することで、どちらのニュースがクエリにより関連しているかを判断できます。

```sql
-- イベント、日付、スコアを返すことで、関連性を判断するのに役立てます。
SELECT event, date, MATCH (news) AGAINST ('オウンゴール バイエルン') AS score
FROM sport_data_whole
WHERE MATCH (news) AGAINST ('+オウンゴール +バイエルン' IN BOOLEAN MODE) limit 10;
```

実行結果は次のとおりです：


また、ブールモードでは、特定のキーワードを除外することも可能です。例えば、ほぼすべてのサッカー試合にはファウルが発生します。どの試合が非常に激しかったか知りたいが、レッドカード、イエローカード、さらにはファウルもなかった試合を探したい場合、ブールモードの `-` 演算子を利用できます。

```sql
-- イエローカード、レッドカード、ファウルがなく激しかった試合を検索します。
SELECT COUNT(*) FROM sport_data_whole
WHERE MATCH (news) AGAINST ('+激しい -イエローカード -レッドカード -ファウル' IN BOOLEAN MODE);
```

実行結果は次のとおりです：

```sql
+----------+
| COUNT(*) |
+----------+
|        0 |
+----------+
1 row in set
```

#### ステップ3：チューニング

##### `TOKENIZE` 関数を使用したチューニング

全文インデックスのクエリ結果が期待通りでない場合、通常は分かち書きの結果が理想的でないためです。seekdb は、分かち書きの効果をテストするための高速な `TOKENIZE` 関数を提供しています。この関数はすべてのトークナイザーとその対応するプロパティをサポートしており、`TOKENIZE` 関数を使用してトークナイザーの処理効果を検証できます。

例えば、以下の手動分かち書きの結果は、辞書が海外のスポーツスターの名前（例：ボアテン、ゲッツェ）を十分にサポートしていないことを示しており、これが名前で検索した際のパフォーマンス低下の原因となっている可能性があります。

1. `TOKENIZE` 関数を使用してトークナイザーの処理効果を検証します：

   ```sql
   -- 中国語のスポーツニュースの分かち書き効果を検証するために、ik_smart 分かち書きモードを使用します
   ```

## MySQLとのパフォーマンス比較

seekdbとMySQLの全文インデックスのパフォーマンス差を比較するため、MySQLの全文インデックス機能を基準としました。MySQLの中国語分かち書き能力は相対的に弱いため、英語データセット`wikir1k`（369,721行、各行平均100語）を用いてパフォーマンスを比較しました。

以下は、自然言語モードとブールモードでの様々なシナリオにおける比較結果です。大量の分かち書きや結果返却が必要なシナリオでは、seekdbのパフォーマンスがMySQLよりも顕著に優れていることがわかります。小規模な結果セットでは、計算量の割合が小さいため、クエリエンジンの優位性は明確ではなく、両エンジンのパフォーマンスは近接しています。

**テスト環境**：seekdbのテスト仕様は8コア16GB、MySQLバージョンは8.0.36 for Linux on x86_64（MySQL Community Server - GPL）を使用しました。

### 自然言語モード

### ブールモード

```sql
-- q1: +高頻度語 -中頻度語
SELECT * FROM wikir1k WHERE MATCH (document) AGAINST ('+and -which -his' IN BOOLEAN MODE);

-- q2: +高頻度語 -低頻度語
SELECT * FROM wikir1k WHERE MATCH (document) AGAINST ('+which  (+and -his)' IN BOOLEAN MODE);

-- q3: +中頻度語 (+高頻度語 -中頻度語)
SELECT * FROM wikir1k WHERE MATCH (document) AGAINST ('+and -carabantes -bufera' IN BOOLEAN MODE);

-- q4: +高頻度語 +低頻度語
SELECT * FROM wikir1k WHERE MATCH (document) AGAINST ('+and +librettists'  IN BOOLEAN MODE);
```

### 性能比較のまとめ

上記のデータ比較から、seekdbは複雑な全文検索を実行する際、自然言語モードであれブールモードであれ、MySQLよりも顕著に優れた性能を発揮していることがわかります。特に、大量の分かち書きや結果の返却サイズが大きいクエリを処理する場合、seekdbの優位性は一層明確になります。これは、デベロッパーやデータアナリストがデータベースを選定する際の有力な参考となり、特に大量のデータを効率的に検索する必要があるアプリケーションシナリオにおいて、seekdbはその強力な性能と柔軟なクエリ能力を明確に証明しています。

seekdbの全文インデックスは、複雑なクエリを処理する際に常に迅速な応答時間を提供できるため、高い同時実行性と高性能な検索を求める実際のアプリケーションシナリオにより適しています。
